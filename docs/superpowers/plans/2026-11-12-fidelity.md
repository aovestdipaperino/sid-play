# Fidelity against a reference player: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure our renders against VICE's reSID renders with an aligned spectral metric, find and fix structural bugs, and queue constant gaps for clean-room rounds.

**Architecture:** A private oracle tool (Python + numpy, scratch virtualenv) renders, aligns and compares. The controller diagnoses each target tune under the bug-hunting rule. Structural fixes land in mos6581 or sid-play with tests. Constant gaps go to isolated clean-room authors with PASS/FAIL thresholds in oracle metrics.

**Tech Stack:** VICE 3.10 `vsid` (Homebrew), Python 3 + numpy (private venv), Rust 2024.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-11-12-fidelity-design.md`. Its "Rule for using the reference" binds every task.
- Reference renders, the oracle tool and its outputs live only in a private scratch directory. Nothing from them is committed.
- No number observed in a reference render may appear in code, tests or comments. Each structural fix is justified from public sources or our own reasoning, and carries a test.
- Acceptance for any change:
  - No corpus tune's spectral distance gets worse by more than 0.5 dB.
  - The targeted tunes improve.
  - `cargo test` and `cargo clippy --all-targets -- -D warnings` pass in every touched repo, and in sid-play with `--features playback` too.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Nothing is pushed or published without the user's go-ahead.
- Clean-room rounds follow the GPL-removal method:
  - an isolated author working from the public sources list, with no emulator sources
  - PASS/FAIL feedback only, at most 3 rounds
  - feedback-driven values labelled as such
  - a public-sources reviewer

### Task 1: Oracle tool (controller, private)

**Files:** `<scratch>/oracle/{venv/, oracle.py, render.sh}`. None are committed.

- [ ] Create the venv, install numpy, and write `oracle.py`.
  - **Load:** read both mono WAVs as float.
  - **RMS envelopes:** compute them in 10 ms frames.
  - **Align:** cross-correlate the envelopes over ±8 s to get the reference offset. Report the offset and the normalised peak (confidence).
  - **Trim:** cut both renders to the overlap.
  - **Spectrogram:** compute an STFT log-spectrogram (2048 window, 512 hop, Hann) folded into octave bands from 31.25 Hz to 16 kHz, in dB with a −90 dB floor.
  - **Metrics:**
    - spectral distance: the RMS over frames and bands of the dB difference
    - envelope correlation
    - per-band mean dB difference
    - tonality median, via the existing `tonality.py`
- [ ] Write `render.sh TUNE SECONDS [SUBTUNE]`. It renders ours with `render --seconds S --out` and VICE with `vsid -console -sounddev wav -soundarg F -soundrate 44100 -sidenginemodel 256 -limitcycles (S+8)*985248 [-tune N]`. The 8 extra seconds cover VICE's boot.
- [ ] Self-check:
  - Our render compared with itself: distance 0 and offset 0.
  - Our render compared with a copy shifted by 1.0 s: offset 1.0 s.
  - Our render compared with VICE on `last_ninja`: confidence above 0.5.

### Task 2: Baseline (controller)

- [ ] Run the oracle on all 17 `data/*.sid` tunes (20 s each), and save the table to `<scratch>/oracle/baseline.txt`.
- [ ] Record each tune's offset and confidence.
- [ ] Mark the target set: the four tunes from the spec, plus any tune whose spectral distance is above the corpus median + 3 dB.

### Task 3: Diagnosis (controller, bug-hunting rule)

For each target tune:

- [ ] Find the time spans and octave bands where the distance concentrates (per-frame and per-band traces).
- [ ] Use our `render --trace` and register logging to see what the tune does there. Check:
  - which voices are active
  - filter routing, cutoff and resonance
  - waveform selections
  - `$D418` writes
  - ADSR settings
- [ ] Form a hypothesis. Write a probe PSID that isolates it, assembled by hand like the fixtures. Confirm it with the oracle.
- [ ] Classify the finding as a structural bug or a constant gap. Write it to the ledger as: evidence, hypothesis, probe result, class.

### Task 4..N: one task per finding (defined from Task 3's output)

- **Structural bug:** do TDD in the owning repo. The test pins the behaviour from the independent justification, never from a reference number. Then run the acceptance check on the corpus.
- **Constant gap:** run a clean-room round. Give the author a brief with the constant's semantics and public sources. The evaluator returns PASS/FAIL on the probe and the target tunes, against thresholds fixed before authoring. Then a reviewer checks it, and `provenance.md` gets an entry.
